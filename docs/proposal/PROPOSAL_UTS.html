1. Problem Statement

Pendataan calon penerima BLT-DD dan penilaian tujuh kriteria kerentanan masih sering dilakukan dengan beberapa berkas spreadsheet yang terpisah. Cara ini menyulitkan pembaruan data, menyulitkan penelusuran riwayat perubahan, dan membuka ruang perbedaan perhitungan antar petugas.

Ketika tujuh kriteria tidak diterapkan dengan urutan dan bobot yang sama, perbandingan antar calon sulit dipertanggungjawabkan. Petugas juga membutuhkan waktu lebih lama untuk menyiapkan bahan musyawarah desa. Prototipe ini menyatukan pendataan calon, validasi formulir, penilaian tujuh kriteria, dan peninjauan urutan prioritas dalam satu alur kerja yang konsisten.

Ruang lingkup

TermasukDi luar lingkup
Login petugas, CRUD data calon, validasi formulir, tujuh kriteria skala 1–5, skor SAW, pengurutan, tampilan responsif Web/Android. Pencairan dana, integrasi sistem pemerintah, data warga nyata, keputusan resmi penerima bantuan, dan verifikasi lapangan.
Batasan akademik. Bobot 20/15/15/15/10/10/15, skala 1–5, dan arah benefit masih asumsi demo. Seluruh nama dan nilai dalam aplikasi adalah data sintetis (Calon Simulasi A–E, SIM-001–SIM-005).

Empat pertanyaan kunci

1. Masalah apa yang diselesaikan?

Pendataan dan penilaian calon yang tersebar, manual, serta sulit ditelusuri.

2. Siapa pengguna utamanya?

Petugas pengelola data BLT-DD di tingkat desa.

3. Mengapa fitur ini diprioritaskan?

CRUD dan validasi menjaga kualitas data; penilaian dan skor SAW adalah inti penentuan urutan.

4. Bagaimana data disimpan?

Firebase Authentication untuk sesi, Cloud Firestore untuk data calon, dengan security rules berbasis role.

5. User Flow

Login→ Beranda→ Data Calon→ Penilaian→ Hasil→ Keluar
  • Login gagal: email kosong/format salah atau kredensial salah menampilkan pesan dan tetap di Login.
  • Login berhasil: membuka Beranda dengan ringkasan dari data termuat.
  • CRUD: Data Calon membuka dialog tambah/ubah yang sama; hapus selalu meminta konfirmasi.
  • Penilaian: pengguna mengubah tujuh nilai; skor dihitung ulang dari nilai tersimpan.
  • Hasil: urutan menurun dengan penjelasan rumus dan pengingat bahwa hasil hanya simulasi.

Rincian langkah dan kondisi gagal: docs/rancangan/USER_FLOW.md.

9. Rancangan Database Firestore

Untuk menjaga alur CRUD awal tetap sederhana, data calon dan tujuh nilai kriteria disimpan dalam satu dokumen. Skor dihitung di klien saat halaman hasil dibuka dan belum disimpan sebagai snapshot historis.

Koleksi calon_penerima

FieldJenisKeterangan
idSimulasistringKode unik dalam daftar termuat, mis. SIM-001.
namaLabelstringLabel calon fiktif, bukan data warga.
dusunstringDusun/kelompok simulasi.
catatanstring (opsional)Maksimum 200 karakter pada form.
scores.C1 … scores.C7integer 1–5Tujuh nilai kriteria.
createdAttimestampServer timestamp saat dibuat (jalur Firebase).
updatedAttimestampServer timestamp saat diubah (jalur Firebase).

Koleksi users

FieldJenisKeterangan
ID dokumenstringUID dari Firebase Authentication.

Dokumen users dibuat manual oleh administrator melalui Console/jalur tepercaya. Rules menetapkan allow write: if false untuk koleksi ini, sehingga user tidak dapat menaikkan role sendiri. Rules masih draft dan wajib diuji di lingkungan non-produksi.

Koleksi rancangan fase berikutnya

KoleksiField utamaStatus
penilaiancalonId, nilaiKriteria, penilaiUid, updatedAtBelum digunakan; nilai masih nested di calon.

Keamanan dan privasi

  • Tidak ada password, private key, token, atau service account di repository.
  • firestore.rules tidak membuka akses publik; hanya user terautentikasi dengan role admin/petugas yang boleh mengakses data operasional.
  • Data contoh memakai label fiktif, bukan NIK atau data warga nyata.
